# 1. EXECUTIVE SUMMARY

## What Is This Project?

The Enterprise Data Quality & Governance Framework is an eight-layer data governance system
that monitors 13 enterprise datasets across a simulated banking organization, tests them daily
against 30 governance controls, detects exceptions, runs an early-warning watchlist, manages
remediation through a full ticket lifecycle, and produces an executive Data Trust Score and
Governance Maturity rating — closing the loop from detection to resolution to board reporting.

## What Business Problem Does It Solve?

Most data quality tooling stops at validation: run a rule, log a failure, stop. That approach
tells you something is wrong but gives no mechanism for prioritization, ownership, escalation,
or proof of resolution. In a regulated environment, that gap is the actual risk — not the data
defect itself, but the absence of a governed response to it. This framework closes that gap by
implementing the full governance lifecycle: **Detect → Assess → Prioritize → Remediate →
Govern → Improve.**

## Why Is Data Quality Important in Banking and Enterprise Reporting?

Banks and financial institutions report to regulators, executives, and the market using data
pulled from operational systems. If that data is incomplete, inaccurate, inconsistent, or stale,
the consequence is not abstract — it is a misstated balance sheet, a missed regulatory deadline,
or a board decision made on numbers that were already wrong. Regulatory regimes (Basel
BCBS 239, FCA data governance expectations) explicitly require demonstrable data quality
controls with audit evidence, not informal assurance.

# 3. GOVERNANCE ARCHITECTURE

The framework is implemented as eight sequential layers, each consuming the output of the
layer before it. All eight layers run inside a single pipeline (`src/pipeline.py`) and write to
an 8-table DuckDB warehouse consumed by a 5-page Streamlit dashboard (`dashboard/app.py`).

### Layer 1 — Data Inventory & Criticality Assessment

| | |
|---|---|
| **Purpose** | Register every dataset in scope with an accountable owner, operational steward, source system, refresh cadence, and regulatory criticality rating |
| **Inputs** | None (foundational registry — manually curated metadata) |
| **Outputs** | `data_inventory` table — 13 rows, 9 columns |
| **Business value** | You cannot govern a dataset you have not registered. This layer is the addressability foundation for every other layer — every control, exception, watchlist entry, and ticket traces back to a `dataset_id` defined here. |

### Layer 2 — Control Rule Definition

| | |
|---|---|
| **Purpose** | Define the testable standard for "good data" across four quality dimensions |
| **Inputs** | Data Inventory (to scope which controls apply to which datasets) |
| **Outputs** | `control_rulebook` table — 30 rows; `DATASET_CONTROLS` mapping (dataset → applicable rule IDs) |
| **Business value** | Converts subjective quality judgement into an objective, auditable standard with a defined pass/fail threshold and severity rating per rule. |

### Layer 3 — Control Testing Framework

| | |
|---|---|
| **Purpose** | Execute every applicable control against every dataset on a daily cadence and persist the result |
| **Inputs** | Data Inventory, Control Rulebook, dataset-control mapping |
| **Outputs** | `control_test_results` table — 1,350 rows over a 30-day window |
| **Business value** | Converts a single point-in-time check into a time series. Trend visibility is what makes early warning (Layer 5) possible — a single day's pass/fail tells you nothing about direction. |

### Layer 4 — Exception Detection

| | |
|---|---|
| **Purpose** | Automatically triage control failures into actionable categories with assigned severity and priority |
| **Inputs** | `control_test_results` (last 7 days) |
| **Outputs** | `exceptions` table — 42 rows: Critical Control Failure, Repeated Control Failure, Regulatory Critical Issue |
| **Business value** | Removes manual triage. A failing email-completeness check and a failing GL-balance check are not equally urgent; this layer encodes that judgement as a rule rather than relying on a human noticing. |

### Layer 5 — Data Quality Watchlist

| | |
|---|---|
| **Purpose** | Detect deterioration trends — null rate, duplicate rate, control failure rate — across a rolling 30-day window, before they manifest as a hard control failure |
| **Inputs** | `control_test_results` (full 30-day history), simulated null/duplicate rate series |
| **Outputs** | `dq_watchlist` table — 13 rows (one per dataset), with 8 in "Watchlist" status and 5 in "Monitor" status |
| **Business value** | This is the differentiating layer of the framework. It is structurally identical to the "Customer Watchlist" and "Fraud Watchlist" concepts used in this author's other two portfolio projects — the same early-warning principle applied to data risk instead of customer or fraud risk. |

### Layer 6 — Remediation Workflow

| | |
|---|---|
| **Purpose** | Track every exception through to verified resolution, with named ownership and an enforced SLA |
| **Inputs** | `exceptions` |
| **Outputs** | `remediation_tickets` table — 42 rows, 16 columns including status, SLA date, root cause, resolution date, verification status |
| **Business value** | Detection without a resolution mechanism is just noise. This layer is what converts the framework from a monitoring tool into a governance operating model — it answers "who is fixing this, by when, and how do we know it's actually fixed." |

### Layer 7 — Governance Reporting

| | |
|---|---|
| **Purpose** | Aggregate Layers 1–6 into two board-level scores: Data Trust Score and Governance Maturity |
| **Inputs** | `control_test_results`, `dq_watchlist`, `remediation_tickets` |
| **Outputs** | `domain_trust_scores` table (10 rows: 9 domains + Enterprise overall); `governance_maturity` table (1 row) |
| **Business value** | A CDO cannot consume 1,350 individual test results. This layer compresses the entire program into two numbers a non-technical executive can act on. |

### Layer 8 — Monthly Governance Review

| | |
|---|---|
| **Purpose** | Generate a structured board-level narrative report — what happened, why, business risk, recommended actions, expected impact |
| **Inputs** | All upstream tables |
| **Outputs** | `MONTHLY_GOVERNANCE_REVIEW.md` (static) + Page 5 of the Streamlit dashboard (live, auto-generated from current warehouse state) |
| **Business value** | Standard governance reporting cadence in regulated organizations. Demonstrates the ability to translate quantitative output into the qualitative narrative a board or audit committee actually consumes. |

## Completeness

Tests whether mandatory fields are populated. Eight rules, ranging from `COMP-001` (Customer ID
Not Null, threshold 100%, Critical) to `COMP-008` (Contact Email Completeness, threshold 95%,
Medium). **Failure example (from live data):** `COMP-002` (Transaction Amount Not Null) recorded
60 failed test executions over the 30-day window — every failure on a Regulatory Critical
dataset (Transaction Ledger) is auto-escalated by Layer 4. **Business impact:** a null
transaction amount cannot be reconciled to the General Ledger, breaking the reconciliation
control (`CONS-006`) downstream.

## Accuracy

Tests whether populated values fall within a valid range or format. Eight rules, including
`ACCU-007` (GL Balance Accuracy, threshold 100%, Critical) and `ACCU-006` (Postcode Format
Accuracy, threshold 97%, Low). **Failure example:** `ACCU-001` (Transaction Amount Positive)
and `ACCU-008` (Product Price Positive) each recorded 60 and 57 failures respectively.
**Business impact:** a negative transaction amount entering the GL without being caught
corrupts the balance reconciliation that `ACCU-007`/`CONS-006` depend on.

## Consistency

Tests whether values agree across datasets or within expected cross-field relationships. Seven
rules, including `CONS-001` (Customer-Account Referential Integrity, 100%, Critical) and
`CONS-004` (Product Code Cross-Dataset Consistency, 99.5%, High). **Failure example:** `CONS-004`
is the single most frequently failing control in the entire framework — **84 failed executions**
over 30 days, more than any other rule. **Business impact:** Product codes used in Orders that
do not exist in Product Master break downstream sales and inventory reconciliation
simultaneously — this is a cross-dataset risk, not a single-dataset risk.

## Timeliness

Tests whether data arrives within its required refresh window. Seven rules, including `TIME-002`
(Transaction Feed SLA, 15-minute window, Critical) and `TIME-007` (Risk Report Delivery SLA,
T+1 09:00, Critical). **Failure example:** `TIME-002` recorded 60 failures and `TIME-001`
(Customer Master Freshness) recorded 51. **Business impact:** a late risk exposure refresh
(`TIME-003`) directly threatens the T+1 regulatory delivery SLA in `TIME-007` — these two
controls are operationally linked even though they are tested independently.

# 6. DATA TRUST SCORE ANALYSIS

## Methodology

The Data Trust Score is computed per domain as:

```
trust_score = avg_control_effectiveness (last 7 days)
              − (3 × count of datasets in that domain on "Watchlist" status)
              − (1 × count of datasets in that domain on "Monitor" status)
```

clamped to the range [0, 100]. The Enterprise Overall score is the simple mean of all domain
scores. Category bands: **Trusted ≥ 90**, **Monitor 75–89**, **At Risk < 75**.

This formula deliberately penalizes a domain for early-warning signals, not just for hard
control failures — a domain can have strong recent control effectiveness and still be pulled
down if its dataset is flagged on the Watchlist. This is intentional: it rewards proactive
governance response, not just retrospective pass rates.

## Lowest Trust Domains

1. **Sales (80.0)** — Sales Performance carries the lowest raw control effectiveness (83.0%)
   of any domain in the framework, compounded by its Watchlist flag.
2. **Operations (81.0)** — Three datasets (Inventory, Orders, Branch Performance) averaging
   90.0% effectiveness, but multiple datasets on Watchlist drag the score down.
3. **Transaction (83.0)** — Transaction Ledger, the framework's highest-priority Watchlist
   entry, sits at 86.0% raw effectiveness before penalty.

## What Drives Trust Score Improvements?

- Sustained control effectiveness above 95% across the 7-day measurement window
- Clearing Watchlist status (each cleared Watchlist flag removes a 3-point penalty)
- Clearing Monitor status (each cleared Monitor flag removes a 1-point penalty)
- No new Critical or Regulatory Critical exceptions in the trailing window

## What Causes Trust Score Deterioration?

- Declining raw control effectiveness (visible in the 30-day trend: 94.25% → 93.39%)
- Accumulating Watchlist flags — each one is a fixed 3-point domain penalty regardless of how
  marginal the deterioration is, by design, to keep early warnings visible at the trust-score
  level rather than being averaged away
- High concentration of Critical-severity rule failures within a single domain (Transaction
  domain carries `COMP-002`, `ACCU-001`, `TIME-002` — three Critical rules — all in the top 10
  most-failing list)

## Why Each Was Flagged — and What It Means

deteriorating simultaneously on a Regulatory Critical dataset with Intraday refresh frequency.

load defect (e.g., a re-run ETL job that re-inserted records) rather than a gradual drift.

records before assuming organic deterioration.

largest single-metric movement in the dataset, consistent with the framework's own root-cause
finding that HR/manual-entry datasets carry the highest Manual Entry Error rate (7 of 42
tickets).

are simultaneously on Watchlist, which is a domain-level signal, not three independent
incidents. Combined with Operations carrying the second-lowest domain trust score (81.0), this
points to a shared upstream cause — most plausibly the OMS source system, which feeds both
Inventory and Orders directly.

# 10. BUSINESS FINDINGS

### Finding 1 — Source System Instability Is the Dominant Root Cause, Not Governance Design

**What happened?** Source System Failure accounts for 13 of 42 remediation tickets (31.0%),
the single largest root cause category, ahead of ETL Failure (9), Mapping Issue (7), Manual
Entry Error (7), and Feed Delay (6).

**Why did it happen?** The governance framework itself — inventory, controls, testing,
detection — is operating as designed (100% control coverage, 100% audit completeness). The
failures are originating upstream, in the source systems (Core Banking, OMS, CRM) feeding the
governed datasets.

**Business risk?** No amount of downstream control tuning fixes an unstable upstream feed. If
this pattern continues, exception volume will stay structurally elevated regardless of how the
governance layer is improved.

**Recommended action?** Escalate a joint review with the Core Banking and OMS platform teams,
using this framework's root-cause data as the supporting evidence — this is a source-system
reliability conversation, not a data governance conversation.

### Finding 2 — All Three Regulatory-Critical-High Datasets Carry the Highest Exception Load

**What happened?** Customer Master (8 exceptions), Transaction Ledger (7), and Risk Exposure
(6) are the top three datasets by exception count — all three are High regulatory criticality.

**Why did it happen?** These three datasets carry the highest density of Critical-severity
controls (e.g., `COMP-001`, `CONS-001`, `COMP-002`, `CONS-002`, `COMP-004`, `CONS-005`), so by
construction they generate more Critical Control Failure exceptions when effectiveness dips.

**Business risk?** These are precisely the datasets used in regulatory submissions. Elevated
exception volume here, even if statistically expected given control density, requires faster
remediation cycles than lower-tier datasets receive.

**Recommended action?** Apply a tighter SLA tier specifically to exceptions on High-regulatory-
criticality datasets (e.g., 12-hour SLA for Critical exceptions on these three datasets,
tighter than the current 1-day default), with mandatory CDO notification.

### Finding 3 — The Data Quality Watchlist Is Functioning as Designed: 100% of Datasets Show an Active Signal

**What happened?** All 13 datasets currently carry either Watchlist (8) or Monitor (5) status —
zero datasets are fully "Clear" in the current 30-day window.

**Why did it happen?** The 30-day control effectiveness trend is in mild decline across the
portfolio (94.25% → 93.39%), so the watchlist's trend-detection logic is correctly surfacing
this broad-based, gradual drift rather than staying silent because no single control has
breached its hard threshold yet.

**Business risk?** If left unaddressed, this broad mild deterioration is likely to convert into
a wave of new Critical exceptions in the next 30-day cycle, since several datasets are already
within a small margin of a hard control breach.

**Recommended action?** Treat this cycle's universal Watchlist coverage as a portfolio-level
early warning, not 13 independent dataset issues. A single root-cause investigation (starting
with Finding 1's source-system hypothesis) is likely to resolve multiple Watchlist entries at
once.

### Finding 4 — SLA Compliance at 50% Is the Single Constraint on Reaching "Optimized" Governance Maturity

**What happened?** Governance Maturity scores 83.0/100 (Managed). Of its four components, three
score 85% or above; SLA Compliance alone scores 50%.

**Why did it happen?** 21 of 42 remediation tickets (50%) breached their defined SLA before
reaching Resolved status, and 14 tickets are currently in Escalated status — the largest single
bucket — indicating that first-line resolution is not closing issues fast enough to avoid
escalation.

**Business risk?** This is an audit risk independent of the underlying data quality issues
themselves: a regulator or internal auditor reviewing this framework would find a governance
process that detects issues reliably but does not yet resolve them within its own stated SLAs.

**Recommended action?** This is the highest-leverage single fix available — raising SLA
Compliance from 50% to roughly 88% would alone lift Governance Maturity above the 90-point
Optimized threshold, with no change required to control coverage, automation, or audit
completeness.

### Finding 5 — Resolution Is Outpacing Verification by a Wide Margin

**What happened?** 10 of 42 tickets are marked Resolved, but only 10 of 42 tickets overall
carry "Verified" status — and 32 of 42 (76.2%) remain "Pending," a category that includes
tickets already marked Resolved awaiting independent sign-off.

**Why did it happen?** The remediation workflow currently treats "Resolved" and "Verified" as
two separate steps, and the verification step has not been operationalized with the same rigor
as the resolution step.

**Business risk?** A "Resolved" ticket that was never independently verified is not actually
audit-grade evidence of a fix — it is a self-reported closure. For Regulatory Critical datasets
specifically, this gap would be the first thing an external auditor would flag.

**Recommended action?** Introduce a mandatory secondary verification step for any ticket on a
Regulatory Critical dataset before it can move from Resolved to Closed, with the verifying
owner distinct from the resolving owner.

### Finding 6 — The Operations Domain Shows a Coordinated, Not Isolated, Deterioration Pattern

**What happened?** All three Operations-domain datasets (Inventory, Orders, Branch Performance)
are simultaneously flagged on the Watchlist, and Operations holds the second-lowest domain
trust score (81.0) in the entire framework.

**Why did it happen?** Inventory and Orders both source from the OMS system; Branch Performance
sources from Branch MIS. A shared OMS-side issue would explain two of the three signals at once,
while Branch Performance's correlation with the other two could indicate a shared downstream
reporting pipeline rather than a coincidence.

**Business risk?** Operational reporting (inventory levels, order fulfilment, branch
performance) feeding into business-critical decisions is currently the least trustworthy
segment of the entire portfolio by trust score, even though none of its datasets carry High
regulatory criticality — a reminder that operational risk and regulatory risk are not the same
axis.

**Recommended action?** Prioritize an OMS feed-stability review ahead of, or in parallel with,
the Core Banking review identified in Finding 1 — Operations is the domain with the most
datasets clustered on Watchlist simultaneously.

### Finding 7 — Consistency Controls, Not Completeness, Are the Framework's Weakest Dimension

**What happened?** `CONS-004` (Product Code Cross-Dataset Consistency) is the single most
frequently failing control in the entire framework at 84 failures — 24 more than the next-
highest control and nearly 1.5x any other rule in the top 10.

**Why did it happen?** Consistency controls test relationships *between* datasets (Orders ↔
Product Master, in this case), which makes them structurally more fragile than single-dataset
Completeness checks — a change in either dataset can break the relationship even if each
dataset individually looks complete and accurate.

**Business risk?** Cross-dataset consistency failures are the hardest category to detect from
within a single dataset's own quality metrics, meaning Orders and Product Master could each
individually report acceptable Completeness and Accuracy scores while still failing this
specific Consistency check.

**Recommended action?** Add a dedicated cross-dataset reconciliation job for product code
mapping that runs ahead of, not just alongside, the standard control test cycle, so mismatches
are caught at the ETL boundary rather than discovered after both datasets have already loaded.

# 13. DATA QUALITY & LIMITATIONS

## Data Completeness

All 8 warehouse tables are fully populated for the current run; there are no missing tables and
no null primary identifiers (`dataset_id`, `rule_id`, `exception_id`, `ticket_id`) in any table.

## Missing Values / Data Quality Issues in the Framework Itself

None observed in the warehouse tables themselves — this is a meta-observation: the governance
framework's own output data is clean, which is a separate claim from "the underlying source
systems it monitors are clean" (they are not, by design, since the dataset is synthetic and
intentionally simulates realistic deterioration).

## Assumptions Made

- Null rate and duplicate rate trends (used by the Watchlist) are simulated using seeded random
  perturbation around dataset-specific base rates, rather than computed from actual record-level
  null/duplicate scans, since the underlying datasets themselves are synthetic event counts, not
  full record sets.
- Control test pass/fail outcomes are generated from a per-dataset "health profile" (stable,
  deteriorating, improving) with seeded randomness, rather than executed against real row-level
  data.
- Remediation ticket status and dates are generated probabilistically based on severity-driven
  SLA windows, not from an actual ticketing system integration.

## Limitations of Synthetic Data

The framework demonstrates governance *mechanics* — how inventory, controls, testing,
exceptions, watchlisting, remediation, and reporting fit together as a system — using
representative, seeded-random data rather than a live production data quality measurement. The
specific numeric findings in this report (e.g., "84 failures on `CONS-004`") are real outputs of
this specific pipeline run, but they describe the simulation's behavior, not an actual bank's
live data quality.

## Limitations of Control Testing

- Controls are tested at an aggregate pass-rate level per dataset-rule pair per day, not at
  individual record granularity — the framework does not currently expose *which* specific
  records failed a given control, only the aggregate failure rate.
- All 13 datasets share a fixed mapping of "applicable controls" (`DATASET_CONTROLS`) defined in
  code; in a production system this mapping would itself need governance (versioning, change
  approval) since it determines what is and is not tested per dataset.

## Potential Enhancements

- Replace simulated null/duplicate rate trends with real column-level profiling against actual
  ingested datasets
- Add record-level failure samples to the Exception registry so a Data Steward can see example
  failing rows, not just an aggregate rate
- Integrate the remediation workflow with a real ticketing system (Jira, ServiceNow) rather than
  a self-contained DuckDB table
- Add control versioning so the Rulebook itself has a change history, supporting governance over
  the controls, not just governance of the data

# 17. INTERVIEW PREPARATION SECTION

## Tell Me About This Project (2-Minute Answer)

"I built an Enterprise Data Quality & Governance Framework that goes beyond standard validation
to implement the full governance lifecycle banks are expected to demonstrate to regulators:
detect, assess, prioritize, remediate, govern, and improve.

It monitors 13 datasets — split across Regulatory Critical, Business Critical, Operational
Critical, and Reference tiers — against 30 governance controls covering Completeness, Accuracy,
Consistency, and Timeliness. Every control runs daily and I keep a 30-day rolling history, which
lets me build an early-warning Watchlist that tracks three trend signals — null rate, duplicate
rate, and control failure rate — and flags a dataset before it actually breaches a hard
threshold.

In my most recent pipeline run, that Watchlist caught all 8 datasets currently showing genuine
deterioration, including a Transaction Ledger entry that's High priority because it's a
Regulatory Critical dataset with a 59.6% null rate increase. Every exception that gets detected
flows into a remediation workflow with a named owner, an SLA, and a root cause category — and I
found that 31% of all root causes trace back to source system instability, not data entry
errors, which is the kind of insight that actually tells you where to invest.

At the top, I roll all of this into two executive numbers: a Data Trust Score, currently 90.6 out
of 100, and a Governance Maturity score, currently 83 — Managed level. And I found that SLA
compliance, at exactly 50%, is the one thing holding the whole program back from Optimized
maturity — which is a much more useful finding than just saying 'data quality needs improvement.'"

## Technical Questions (10, with Answers)

1. **Why DuckDB instead of a traditional data warehouse?**
   DuckDB is SQL-compliant, requires no server, and handles analytical workloads (aggregation
   across 1,350+ test rows) efficiently in-process. For a portfolio project it keeps everything
   self-contained and reproducible. The SQL patterns I used translate directly to Snowflake or
   BigQuery in production.

2. **How does the Watchlist actually compute "deteriorating" vs. "stable"?**
   I split the 30-day window into an early half (days 1–15) and a recent half (days 16–30),
   compute the percentage change in each of the three signals, and classify anything beyond a
   ±10% move as Deteriorating or Improving, otherwise Stable. Two or more deteriorating signals
   puts a dataset on the Watchlist; one puts it on Monitor.

3. **Why is your Pass/Fail rate only 20% when your average control effectiveness is 94%?**
   Because Fail is threshold-relative, not absolute — 12 of my 30 controls are Critical
   severity with thresholds at 99% or 100%. A 94% average effectiveness against a 99–100% bar
   produces a high technical fail count even though the underlying data quality is reasonably
   strong. That's a deliberate design choice mirroring how real Critical banking controls are
   held to near-zero tolerance.

4. **How is the Data Trust Score different from just averaging control effectiveness?**
   It explicitly penalizes Watchlist and Monitor flags on top of raw effectiveness — a 3-point
   penalty per Watchlist dataset, 1-point per Monitor dataset, in that domain. That means a
   domain can have decent recent pass rates and still get pulled down if it's showing an
   early-warning trend, which rewards proactive response rather than just retrospective scoring.

5. **What's the actual database schema?**
   Eight tables: `data_inventory`, `control_rulebook`, `control_test_results`, `exceptions`,
   `dq_watchlist`, `remediation_tickets`, `domain_trust_scores`, `governance_maturity`. Every
   downstream table references `dataset_id` and/or `rule_id` back to the first two.

6. **How would you scale this to thousands of datasets?**
   The architecture already separates the registry (`data_inventory`) from the rule logic
   (`control_rulebook`) from the testing engine — adding a dataset means adding a row and a
   control mapping, not new code. For real scale I'd add orchestration (Airflow/Prefect), swap
   DuckDB for a cloud warehouse, and likely partition the `control_test_results` table by date.

7. **What's missing from this for production use?**
   Real record-level null/duplicate profiling instead of the simulated trend proxies I'm
   currently using, integration with an actual ticketing system instead of the self-contained
   `remediation_tickets` table, and a dedicated test suite — which I've identified as the next
   concrete step.

8. **Why do you have 12 Critical-severity controls out of 30?**
   I deliberately weighted severity toward the Regulatory Critical datasets — Customer Master,
   Transaction Ledger, Risk Exposure, General Ledger — because those are the ones that, if wrong,
   create direct regulatory exposure. The severity distribution isn't arbitrary; it reflects
   where the actual business risk concentrates.

9. **How did you generate the synthetic test data realistically?**
   Each dataset has a seeded "health profile" — stable, deteriorating, or improving — that
   drives a daily pass rate with a small trend adjustment and noise term. I used `random.seed(42)`
   and `np.random.seed(42)` so the pipeline is fully reproducible run to run.

10. **What was the single most interesting finding from analyzing the warehouse output?**
    That `CONS-004`, a cross-dataset Consistency control between Orders and Product Master, is
    the single most frequently failing control in the framework at 84 failures — almost double
    most other rules. Consistency controls are structurally more fragile than single-dataset
    checks because they can fail even when each individual dataset looks fine in isolation.

## Business Questions (10, with Answers)

1. **Why does data quality matter to a bank specifically?**
   Because banks report to regulators and the market using data pulled directly from
   operational systems. A data quality defect doesn't stay technical — it becomes a misstated
   balance sheet line, a missed regulatory deadline, or a board decision built on a number that
   was already wrong.

2. **What's the business case for an early-warning Watchlist instead of just fixing failures as
   they happen?**
   Cost and disruption scale with how late you catch a problem. Catching a null-rate increase
   before it breaches a hard control threshold gives you time for a planned fix instead of an
   emergency one — and it keeps the issue out of a regulatory report entirely. The specific lead
   time this buys is a design intent, not a backtested figure: `dq_watchlist` stores a
   point-in-time snapshot rather than dated history, so a claim like "N days before" can't be
   verified against this warehouse's data (see `INTERVIEW_PREP_OBJECTIONS.md` Q6). What's
   verified instead: 100% of currently open exceptions occur on datasets the watchlist had
   already flagged before the exception was logged.

3. **How do you decide what's "Critical" severity vs. "Low"?**
   By the consequence of the control failing, not the dataset's name. A null Customer ID
   (`COMP-001`) breaks every downstream join — Critical. A malformed postcode (`ACCU-006`)
   degrades a marketing segment slightly — Low. Severity should track business consequence.

4. **What does a 50% SLA compliance rate actually mean for the business?**
   It means half of the issues this framework correctly detected took longer than their agreed
   deadline to resolve. That's not a data quality failure — it's a process and capacity issue in
   the remediation organization, and it's the single biggest improvement opportunity I found.

5. **Why are Sales, Operations, and Transaction the lowest-trust domains?**
   Sales and Transaction both carry a single dataset each with below-90% recent control
   effectiveness; Operations has three datasets simultaneously on the Watchlist. None of the
   three are "bad" in absolute terms — they're just where the current 30-day deterioration trend
   is concentrated.

6. **How would you explain "Governance Maturity" to a non-technical stakeholder?**
   It's a single 0–100 score answering "how mature is our data governance program overall,"
   built from four ingredients: how much of our data is covered by controls, how much of that
   testing is automated, how well we hit our own resolution deadlines, and how complete our audit
   trail is. We're at 83 — "Managed" — held back almost entirely by the deadline-hitting piece.

7. **What would you tell a board member who asks "can I trust this quarter's numbers?"**
   "Enterprise-wide, yes — we're at 90.6 out of 100, in the Trusted band. But I'd flag that
   Transaction Ledger specifically is on our High-priority Watchlist this cycle, so I'd want
   confirmation that figure has been reviewed before it goes into anything regulator-facing."

8. **How does this connect to regulatory frameworks like BCBS 239?**
   BCBS 239 requires banks to demonstrate accurate, complete, timely risk data aggregation with
   documented controls — which is exactly the structure here: a control rulebook with defined
   thresholds, a 30-day audit trail of test execution, and a documented remediation process with
   SLAs. It's the same governance pattern, built at portfolio scale.

9. **What's the ROI of a framework like this?**
   I deliberately avoid quoting a fabricated cost-saving number — that's not credible without
   real production data. The honest value proposition is risk reduction: faster detection,
   documented audit evidence, and a measurable maturity trajectory, which is how this is actually
   discussed in governance and audit committee settings.

10. **If you only had budget to fix one thing from this report, what would it be?**
    SLA compliance in the remediation workflow. It's the only governance maturity component
    below 85%, and fixing it alone is mathematically sufficient to move the program from
    "Managed" to "Optimized" — a clearer, higher-leverage ask than spreading effort across
    several smaller improvements.

## Governance Questions (10, with Answers)

1. **What's the difference between a control and an exception in your framework?**
   A control is a defined, testable rule with a threshold (e.g., `COMP-001`, 100% threshold). An
   exception is what gets created when a control test result crosses into a business-significant
   pattern — a Critical-severity failure, a 3-day repeated failure, or any failure on a
   Regulatory Critical dataset. Not every failed test becomes an exception; the exception layer
   is the triage logic on top of raw test results.

2. **Who "owns" a dataset in your governance model, and why does that matter?**
   Every dataset in `data_inventory` has both an Owner (accountable, typically a Head of
   function) and a Steward (operational, day-to-day). This mirrors standard data governance
   practice (e.g., DAMA-DMBOK) — accountability and operational responsibility are deliberately
   separated so escalation has a clear destination.

3. **How does root cause classification feed back into governance improvement?**
   The five root cause categories — Source System Failure, ETL Failure, Mapping Issue, Manual
   Entry Error, Feed Delay — let you aggregate tickets by underlying cause rather than just by
   symptom. In my current run, that aggregation revealed Source System Failure as 31% of all
   tickets, which redirects the fix conversation upstream rather than at the governance layer
   itself.

4. **What's your audit trail story if a regulator asks for evidence?**
   Every one of the 1,350 control test executions in the last 30 days is individually timestamped
   and stored with its pass/fail outcome and effectiveness percentage in `control_test_results`.
   That's a complete, queryable audit trail — Audit Completeness scores 100% in my Governance
   Maturity breakdown specifically because of this.

5. **How do you handle a control whose threshold might be miscalibrated?**
   I'd flag it the same way I flagged `CONS-004` in this report — a control failing far more
   often than its peers is itself a signal worth investigating, either as a genuine systemic
   issue or as evidence the threshold itself needs governance review. Thresholds aren't
   permanent; they should be revisited periodically, which I noted as a recommended enhancement
   (control versioning).

6. **What's the difference between "Resolved" and "Verified" in your remediation workflow, and
   why does it matter?**
   Resolved means the assigned owner believes the issue is fixed. Verified means an independent
   check confirmed it. I found a real gap here — 76% of tickets are still Pending verification,
   including some already Resolved — which is exactly the kind of self-reported-closure risk an
   auditor would flag, and exactly why I recommend separating them into two enforced workflow
   gates with different owners.

7. **How does the Watchlist avoid becoming "alert fatigue" if every dataset eventually shows
   some signal?**
   That's a real risk I'd actively manage — in this cycle, literally 13 of 13 datasets show some
   active signal. The mitigation is the priority field: only 1 of the 8 Watchlist entries is
   High priority, the rest are Medium or Low. Priority, not just status, is what should drive
   where attention actually goes.

8. **How would you defend the severity weighting (12 Critical, 11 High, 6 Medium, 1 Low) if
   challenged?**
   By tracing each severity back to a stated business consequence, not an arbitrary label —
   which is exactly what Section 4 of this report does for each quality dimension. If a
   stakeholder disagrees with a specific rule's severity, the conversation should be about the
   stated business consequence, not the label itself.

9. **What governance maturity model are you using, and why that one?**
   A standard four-stage model (Initial → Developing → Managed → Optimized), which mirrors
   CMMI-style maturity frameworks commonly used in enterprise governance contexts. I built my own
   four-component scorecard (Control Coverage, Automation, SLA Compliance, Audit Completeness)
   rather than adopting a heavier industry framework wholesale, to keep it interview-explainable
   while still being structurally sound.

10. **What would "Optimized" maturity actually look like for this framework?**
    Mathematically: all four components above roughly 88–90%. Practically: SLA Compliance closed
    to the 88%+ range (currently 50%), full ticket verification (currently 24% verified), and
    sustained Control Coverage and Audit Completeness at their current 100% levels. I've already
    identified SLA Compliance as the one component standing between Managed and Optimized.

# 20. FINAL EXECUTIVE CONCLUSION

## What Was Built

A complete, eight-layer data governance framework — not a validation script, a governance
system. It registers 13 datasets with named accountability, tests them daily against 30
controls spanning the four standard quality dimensions, automatically triages failures into
prioritized exceptions, runs a trend-based early-warning watchlist, tracks every issue through
an SLA-enforced remediation workflow to verified resolution, and compresses the entire program
into two board-consumable scores.

## What Business Problem It Solves

It closes the gap between *detecting* a data quality problem and *governing* the organization's
response to it — the gap that actually matters in a regulated environment, where the absence of
a documented, accountable, auditable response is the real exposure, not the underlying defect
itself.

## Key Achievements (This Run)

- 90.6/100 Enterprise Data Trust Score, correctly differentiating three below-Trusted domains
  (Sales, Operations, Transaction) from six Trusted domains
- 83.0/100 Governance Maturity (Managed), with a single, precisely identified lever — SLA
  Compliance at 50% — standing between the current state and Optimized
- Correct identification of Source System Failure as the leading root cause (31% of all
  tickets) through aggregate root-cause analysis, redirecting the fix conversation upstream
  rather than into the governance layer itself
- Early identification of a High-priority Watchlist flag on a Regulatory Critical, Intraday-
  refresh dataset (Transaction Ledger) before any hard control breach occurred

## Why It Matters

A bank does not fail an audit because a number was wrong once. It fails an audit because there
was no governed process to catch the number being wrong, prioritize the fix, track it to
resolution, and prove it was actually fixed. This framework demonstrates exactly that process,
end to end, with real computed evidence at every layer rather than a conceptual diagram.

## Why This Project Demonstrates Data Quality, Governance, Controls, Risk Management, and Banking Operations Understanding

- **Data Quality:** four quality dimensions, 30 calibrated controls, real measured effectiveness
  trends over a 30-day window
- **Governance:** named ownership and stewardship at the dataset level; a documented, auditable
  control rulebook; a structured monthly board narrative
- **Controls:** severity-tiered thresholds matched to actual business consequence, not applied
  uniformly across all datasets
- **Risk Management:** explicit regulatory criticality tiering driving differentiated escalation
  and SLA treatment; trend-based early warning rather than purely reactive detection
- **Banking Operations Understanding:** correct recognition that operational risk (Operations
  domain cluster) and regulatory risk (High-criticality datasets) are distinct axes requiring
  different prioritization logic — and that root cause, not symptom, is where the real fix
  belongs
