## The Headline Findings

**Too lenient — DS-003:** Risk Exposure failed **100% of its 150 control tests** over the full 30-day window, yet its Risk domain scores **94.1/100, "Trusted."** The Data Trust Score formula averages continuous `control_effectiveness` (94.8–95.1%, just under each rule's 98–100% threshold) rather than counting binary pass/fail outcomes.

**Too strict — DS-012:** Branch Reference's duplicate rate moved **0.129 percentage points** (0.0108% → 0.14%) on a monthly-refreshed dataset, and the framework reported it as a **"1192.9% increase"** — the largest single movement on the watchlist.

*Note on the DS-012 figure:* cite **1,192.9%** (the pipeline's own stored `watchlist_reason`, computed from the unrounded value), not 1,300%. The stored `duplicate_rate_early` column is rounded to 2dp, and recomputing from it gives 1,300% — an earlier version of these docs made exactly that mistake. Related: the `max(x, 0.01)` floor in the trend formula is **not** the cause here (the true baseline 0.01083 is above it, and the floor never engages anywhere in this dataset); the cause is percentage-change against a near-zero baseline.

Full detail and demonstrated fixes: `docs/DISCOVERY_NARRATIVE.md` Section 6, `sql/v2_rebuild/SQL_COMPARISON.md` Edge Case 1, `notebooks/01_governance_analysis.ipynb`.

## Reproducibility Note (empirically tested, 29 Jul 2026)

An earlier version of this note claimed the metrics above "shift on every pipeline re-run." **That was over-cautious and turned out to be wrong.** The pipeline was actually re-run and the resulting database diffed against the previous one, table by table. What changed and what didn't:

**Unchanged — every metric in the table above:** Enterprise Trust Score (90.6), all 9 domain scores, control pass/fail split (272/1,350), DS-003's 100% fail rate, DS-012's duplicate rates (0.01 → 0.14), SLA breach totals (21/42) *and* the breakdown by severity, governance maturity (83.0), the chronic-failure pair count, and every control-category fail rate. `random.seed(42)` / `np.random.seed(42)` (`src/pipeline.py:15-16`) makes the simulation genuinely reproducible.

**Changed — absolute dates only:** the 30-day window slid from 2026-05-21 → 2026-06-19 to end on the new run date, and ticket `open_date`/`sla_date` slid with it. Because ticket ages *and* the SLA comparison both shift together, the relative outcomes (who breached, by how much) are preserved.

**One genuine staleness effect, and it's the interesting one:** `sla_breach` is written once at pipeline-run-time and never re-evaluated. As real calendar time passes without a re-run, stored flags drift from live truth — currently 11 of 42 tickets have crossed their SLA date but still carry the `sla_breach = False` written weeks ago. Re-running the pipeline collapses that discrepancy to **0 of 42** (verified). This is exactly the drift a scheduled daily run is designed to absorb, and it is documented with ticket IDs in `sql/v2_rebuild/SQL_COMPARISON.md`.

So: figures are reproducible, dates are not, and the stored-vs-live SLA gap is a real property of the design rather than randomness.

## Known Limitations

Stated plainly, once, here — not re-litigated across every other document:

1. **All data is synthetic.** Every number in this project — DS-003's 100% failure rate, DS-012's false positive, the 50% SLA breach rate, the Consistency-control concentration — is generated by `src/pipeline.py`, not sourced from a real banking system. The analytical findings (a scoring formula that can be gamed by near-threshold averaging; a trend formula sensitive to near-zero baselines) are real, verified behaviors of this framework's own design, and the technique used to find them — stress-testing a scoring system against its own edge cases — generalizes to real data. But the underlying data itself has never encountered a real production data quality problem (encoding drift, schema migrations, partial batch loads, etc.). Running this framework against a real public dataset is a natural next step, not attempted in this project.
2. **No external stakeholder validation.** Every design choice — 30 controls, the 8-layer architecture, the trust-score weights, the SLA thresholds (1/3/7/14 days by severity) — reflects this author's own design judgment. No data governance professional, CDO, or industry framework (DAMA DMBOK, DCAM, BCBS 239) was consulted during design; where this project references those frameworks (see `docs/DISCOVERY_NARRATIVE.md`, `GOVERNANCE_RECOMMENDATION_MEMO.md`), it is naming them as what a redesign would draw from, not claiming their validation.
3. **This is a framework-design project demonstrated through stress-testing, not a real-data discovery project.** The strongest findings here (DS-003, DS-012, the SLA severity inversion) came from interrogating this project's own design choices against its own generated data — a legitimate and valuable analytical exercise, but a different kind of work than finding an unexpected pattern in real-world data that resisted expectations. Both are worth doing; this project is honestly the former, and is presented as such rather than overclaiming the latter.
